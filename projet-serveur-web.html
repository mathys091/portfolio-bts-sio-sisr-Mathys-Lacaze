PPE 06 Services Cybersécurité Février — avril 2026

Hébergement web sécurisé et reverse proxy

Publier proprement plusieurs services web depuis la DMZ derrière un point d’entrée unique : chiffrement, en-têtes de sécurité, isolation par conteneurs et protection contre les tentatives d’intrusion.

Contexte et besoin

L’entreprise souhaitait publier trois services : un site vitrine, un intranet documentaire réservé aux salariés et un outil de tickets accessible aux clients. La solution existante consistait à ouvrir un port différent par service depuis Internet, sans certificat valide et sans journalisation exploitable.

Les besoins exprimés :

  • une seule adresse d’entrée en HTTPS, avec un sous-domaine par service ;
  • des certificats reconnus, renouvelés automatiquement ;
  • une isolation entre les services : la compromission de l’un ne doit pas atteindre les autres ;
  • une protection contre les tentatives d’authentification répétées.

Architecture retenue

Mise en œuvre

  1. Préparation du serveur Machine virtuelle Debian dans la DMZ, mises à jour automatiques de sécurité, authentification SSH par clé uniquement, connexion root désactivée.
  2. Conteneurisation des applications Un conteneur par service, réseaux Docker distincts, volumes nommés pour les données persistantes, exécution des processus sans privilèges root.
  3. Reverse proxy Nginx en frontal : un bloc serveur par sous-domaine, redirection systématique de HTTP vers HTTPS, transmission de l’adresse réelle du client aux applications.
  4. Certificats Obtention de certificats Let’s Encrypt par validation HTTP, renouvellement automatique testé en simulation avant mise en production.
  5. Durcissement TLS et en-têtes TLS 1.2 et 1.3 uniquement, suites de chiffrement modernes, HSTS, protection contre le détournement de clic et le reniflage de type de contenu.
  6. Protection contre les attaques Fail2ban sur les journaux Nginx et SSH, limitation du nombre de requêtes par adresse sur les pages d’authentification, blocage des méthodes HTTP inutiles.
  7. Sauvegarde et supervision Export quotidien des volumes et des bases, contrôle du certificat et du code de réponse depuis Zabbix (PPE 04).

Extrait de configuration Nginx

server {
    listen 443 ssl;
    http2 on;
    server_name support.exemple.fr;

    ssl_certificate     /etc/letsencrypt/live/support.exemple.fr/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/support.exemple.fr/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options    "nosniff" always;
    add_header X-Frame-Options           "SAMEORIGIN" always;
    add_header Referrer-Policy           "strict-origin-when-cross-origin" always;

    # Limitation des tentatives d'authentification
    location /login {
        limit_req zone=authentification burst=5 nodelay;
        proxy_pass http://127.0.0.1:8083;
    }

    location / {
        proxy_pass         http://127.0.0.1:8083;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name support.exemple.fr;
    return 301 https://$host$request_uri;
}

Identité numérique du domaine

La publication d’un service s’accompagne de la protection du nom de domaine, souvent négligée : sans enregistrements d’authentification du courrier, n’importe qui peut envoyer des messages en se faisant passer pour l’organisation.

Difficultés rencontrées

  • Journaux inexploitables derrière le proxy. Toutes les requêtes apparaissaient comme provenant du reverse proxy, rendant Fail2ban inefficace côté application. La transmission de l’adresse réelle du client et sa prise en compte dans les applications ont rétabli une journalisation utile.
  • Validation du certificat en échec. La demande échouait car le port 80 n’était pas ouvert temporairement pour la validation. Comprendre le mécanisme du défi HTTP m’a évité de désactiver des règles de filtrage « au hasard ».
  • Conteneurs exécutés en root. La première version utilisait des images officielles sans configuration d’utilisateur. Le passage à un utilisateur non privilégié a demandé d’ajuster les droits sur les volumes, mais réduit fortement l’impact d’une compromission.

Bilan et pistes d’amélioration

Ce projet fait le lien entre l’infrastructure et les services rendus aux utilisateurs. Il m’a montré que la sécurité d’un service web se joue à plusieurs niveaux — réseau, transport, application — et qu’aucun d’eux ne suffit seul.

  • Ajouter un pare-feu applicatif web (ModSecurity) avec un jeu de règles adapté.
  • Mettre en place une politique de sécurité du contenu stricte sur les applications.
  • Automatiser le déploiement des conteneurs depuis un dépôt Git.
  • Passer la publication de l’intranet derrière une authentification unique.
